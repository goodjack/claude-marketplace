# 文件類型的骨架

寫某一類文件、不確定該有哪些節時讀。骨架是鷹架不是範本：依讀者當下要做的事挑需要的節，不適用就省略，不建空結構、不填「無」湊數。每一類都先照 `SKILL.md` 第 2 節寫開頭，開頭的上限照舊。

## 目錄

1. 先判斷是哪一類
2. 說明
3. 操作
4. 參考
5. 教學
6. 決策與設計
7. 狀態更新
8. 事件報告

## 先判斷是哪一類

類型依讀者讀這份文件時要做的事來分，不依內容主題分。分類參考 [Diátaxis](https://diataxis.fr/how-to-use-diataxis/) 與 [DITA 的資訊分型](https://docs.oasis-open.org/dita/dita/v1.3/cos02/part1-base/archSpec/base/information-typing.html)，後三類是工作文件常見的補充。

| 讀者要做的事 | 類型 |
| --- | --- |
| 理解為什麼、怎麼運作 | 說明 |
| 已經知道要做什麼，要把它做完 | 操作 |
| 查某個值、參數或規格 | 參考 |
| 第一次學會一件事 | 教學 |
| 拍板，或理解一個設計為什麼長這樣 | 決策與設計 |
| 掌握進度，知道要不要介入 | 狀態更新 |
| 了解事件經過與後續行動 | 事件報告 |

一份文件同時要服務兩種任務時，拆成兩份，或分節各自照對應的骨架寫。最常見的混雜是把說明塞進操作步驟裡，讀者照做時被背景擋住。

Diátaxis 自己強調它不是範本，不要先建好四類的空結構再填內容（[整理](https://stevearrants.substack.com/p/documentation-frameworks-a-field)）。下面每一類的節名也只是常見選項。

## 說明

讀者要建立理解，通常不急著動手。

- 開頭：這件事是什麼、為什麼重要，一兩句。
- 主體：依讀者心裡的問題排序，每節回答一個問題。因果與權衡用短段落，有分支或迴圈的關係考慮用圖。
- 必要時：跟其他做法的比較、已知限制。
- 常見錯法：混進操作步驟或完整參數表。這兩類各自拆出去，原處留一句連結。

## 操作

讀者已經知道目標，要一步步把它做完（[Diátaxis: How-to guides](https://diataxis.fr/how-to-guides/)）。

- 開頭：做完會得到什麼結果，適用什麼情況。
- 前置條件：真正必要的才列，放在第一步之前。
- 步驟：編號清單，一個步驟對應一個讀者的決定或動作，必要時附預期結果。
- 驗證：怎麼確認做成功了。
- 必要時：常見錯誤與處理，放在步驟之後。
- 常見錯法：在步驟裡解釋設計理由。讀者照做時用不到的理由移到說明文件。

## 參考

讀者回頭查某個值，不會從頭讀（[Diátaxis: Reference](https://diataxis.fr/reference/)）。

- 結構跟著被描述的東西走，例如依參數、依 API 端點、依錯誤碼排列，讓人用名稱找得到。
- 每一項的寫法一致，多屬性用表格。
- 只寫事實與限制，不寫教學或論證。
- 常見錯法：同一類項目各自用不同格式，讀者無法掃讀比對。

## 教學

讀者第一次學，要先成功一次（[Diátaxis: Tutorials](https://diataxis.fr/tutorials/)）。

- 開頭：學完能做到什麼，需要先準備什麼。
- 最短成功路徑：每一步都有可見的結果，讓讀者確認自己沒走錯。
- 之後：延伸做法、說明與參考的連結。
- 常見錯法：詞彙表、架構介紹與故障排除擋在第一次成功之前。

## 決策與設計

讀者要拍板，或理解設計為什麼長這樣（[Design docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)）。

- 開頭：要決定什麼、建議方案、要讀者做的事。
- 脈絡與問題：為什麼現在要決定。
- 目標與非目標：非目標明列這次刻意不做的事，讓讀者知道範圍邊界，也避免之後被當成遺漏。
- 方案與取捨：建議方案，以及替代方案為什麼沒選。比較多屬性時用表格。
- 風險與待確認：每項標狀態。
- 決策紀錄的修改例外：已定案的紀錄不改原文，另開一份新紀錄說明取代哪一份，舊紀錄標「已取代」並指向新紀錄（[架構決策紀錄的慣例](https://adr.github.io/)）。
- 常見錯法：只列建議方案，讀者看不出比較過什麼。

## 狀態更新

讀者要掌握進度，判斷要不要介入。

- 開頭：現況一句，以及需要讀者做的事。沒有就寫明不用處理。
- 日期與狀態：文件上標出這份狀態是哪一天的，期限與事件寫絕對日期。
- 主體：已完成、進行中、需要協助、下一步。需要協助的項目寫清楚需要誰做什麼。
- 常見錯法：照時間順序寫成工作流水帳，讀者找不到要他決定的事。

## 事件報告

讀者要了解事件經過、影響與後續行動，焦點放在系統與流程，不放在個人（[Google SRE: Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)）。

- 開頭：發生什麼、影響範圍與期間、目前狀態。
- 時間線：絕對時間並標時區，三件以上用表格。
- 原因：觀測事實與推論分開寫，排除的假設條列，不逐段展開。
- 處置與行動項目：每項寫 owner 與期限，owner 未知就標「待指派」，不猜。
- 常見錯法：把調查過程的查詢與逐行程式碼放進報告。這些屬於查證用的部分或另存。
