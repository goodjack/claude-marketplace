# 文件類型的骨架

寫某一類文件、不確定該有哪些節時讀。骨架是鷹架不是範本：依讀者當下要做的事挑需要的節，不適用就省略，不建空結構、不填「無」湊數。每一類都先照 `SKILL.md` 第 2 節寫開頭：第一段 2～4 句講發生什麼、為什麼現在處理、結論或要讀者做什麼。節標題用主題短語，不用問句或金句。

## 目錄

1. 先判斷是哪一類
2. 說明
3. 操作
4. 參考
5. 教學
6. 決策與設計
7. 狀態更新
8. 事件報告

## 先判斷是哪一類

類型依讀者讀這份文件時要做的事來分，不依內容主題分。分類參考 [Diátaxis](https://diataxis.fr/how-to-use-diataxis/) 與 [DITA 的資訊分型](https://docs.oasis-open.org/dita/dita/v1.3/cos02/part1-base/archSpec/base/information-typing.html)，後三類是工作文件常見的補充。

| 讀者要做的事 | 類型 |
| --- | --- |
| 理解為什麼、怎麼運作 | 說明 |
| 已經知道要做什麼，要把它做完 | 操作 |
| 查某個值、參數或規格 | 參考 |
| 第一次學會一件事 | 教學 |
| 拍板，或理解一個設計為什麼長這樣 | 決策與設計 |
| 掌握進度，知道要不要介入 | 狀態更新 |
| 了解事件經過與後續行動 | 事件報告 |

一份文件同時要服務兩種任務時，拆成兩份，或分節各自照對應的骨架寫。最常見的混雜是把說明塞進操作步驟裡，讀者照做時被背景擋住。

Diátaxis 自己強調它不是範本，不要先建好四類的空結構再填內容（[整理](https://stevearrants.substack.com/p/documentation-frameworks-a-field)）。下面每一類的節名也只是常見選項。

## 說明

讀者要建立理解，通常不急著動手。

- 開頭：這件事是什麼、為什麼重要，一兩句。
- 主體：依讀者想知道的順序排，每節講一個主題。因果與權衡用短段落，保留連接句，有分支或迴圈的關係考慮用圖。
- 必要時：跟其他做法的比較、已知限制。
- 常見錯法：混進操作步驟或完整參數表。這兩類各自拆出去，原處留一句連結。

## 操作

讀者已經知道目標，要一步步把它做完（[Diátaxis: How-to guides](https://diataxis.fr/how-to-guides/)、[Google: Procedures](https://developers.google.com/style/procedures)）。

- 開頭：第一句寫適用的人與情境，讓讀者一眼知道是不是寫給自己，接著寫做完會得到什麼。會影響該不該讀的限制（例如只適用某個版本或作業系統）也放在開頭。
- 前置條件：真正必要的才列，放在第一步之前。
- 步驟：編號清單，一個步驟對應一個讀者的決定或動作。每步附一句原因，寫成「為了 X，做 Y」，讓讀者知道為什麼要做。長篇解釋另外連到說明文件。必要時附預期結果。
- 驗證：怎麼確認做成功了。
- 故障排除：放在最後，用表格，欄位是「看到什麼、原因、怎麼修」，讀者依症狀找到自己那一列，不必依序檢查。
- 範圍外：這份不處理的事放在文末，讓讀者心裡有底。
- 章節標題可以寫成要完成的事，例如「設定公司帳號」。
- 常見錯法：步驟只有指令沒有原因，讀者遇到例外不知道能不能跳過。另一種是在步驟裡展開設計理由，讀者照做時被擋住。

## 參考

讀者回頭查某個值，不會從頭讀（[Diátaxis: Reference](https://diataxis.fr/reference/)）。

- 結構跟著被描述的東西走，例如依參數、依 API 端點、依錯誤碼排列，讓人用名稱找得到。
- 每一項的寫法一致，多屬性用表格。
- 只寫事實與限制，不寫教學或論證。
- 常見錯法：同一類項目各自用不同格式，讀者無法掃讀比對。

## 教學

讀者第一次學，要先成功一次（[Diátaxis: Tutorials](https://diataxis.fr/tutorials/)）。

- 開頭：學完能做到什麼，需要先準備什麼。
- 最短成功路徑：每一步都有可見的結果，讓讀者確認自己沒走錯。
- 之後：延伸做法、說明與參考的連結。
- 常見錯法：詞彙表、架構介紹與故障排除擋在第一次成功之前。

## 決策與設計

讀者要拍板，或理解設計為什麼長這樣（[Design docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)、[Amazon 的敘事備忘錄](https://www.aboutamazon.com/news/company-news/2017-letter-to-shareholders)）。讀者常是被轉來、還不知道這件事的人，所以先讓他懂全貌，再請他決定：

1. 開頭：一段 2～4 句的全貌，講發生什麼、為什麼現在要決定、建議或要讀者做什麼（`SKILL.md` 第 2 節）。結論不晚於第二段。
2. 接下來二選一，看讀者要不要先懂經過才能判斷：
   - 讀者已懂全貌，接著寫要決定的事：選項與建議，每個選項一句代價或風險，比較多屬性時用表格。
   - 讀者需要先懂經過，接著依發生順序講經過與原因，再寫要決定的事。
3. 原因與依據：事實直接講，推論在當句用「推測」「可能」這類詞限定。依據集中在這一節，不逐句貼標籤。
4. 還不知道的事與排除的假設：只列會影響決定的。
5. 目標與非目標（設計文件需要時）：非目標明列這次刻意不做的事，讓讀者知道範圍邊界，也避免之後被當成遺漏。
6. 查證用的部分（需要時）：逐項證據、時間、筆數、錯誤碼，以及替代方案的完整比較。界定適用期間、必要分母或操作分支的數字留在上方。

太長時依序把細節移到後面、刪重複、最後才刪事項，因果與轉折的連接句不刪。

- 決策紀錄的修改例外：已定案的紀錄不改原文，另開一份新紀錄說明取代哪一份，舊紀錄標「已取代」並指向新紀錄（[架構決策紀錄的慣例](https://adr.github.io/)）。
- 常見錯法：開頭沒講發生什麼，劈頭就要讀者決定，讀者還沒懂全貌，不敢放心判斷。另外兩種：證據一、證據二、證據三整組放在前面，建議被排到「還不知道的事」之後，以及只列建議方案，讀者看不出比較過什麼。

## 狀態更新

讀者要掌握進度，判斷要不要介入。

- 開頭：現況一句，以及需要讀者做的事。沒有就寫明不用處理。
- 日期與狀態：文件上標出這份狀態是哪一天的，期限與事件寫絕對日期。
- 主體：已完成、進行中、需要協助、下一步。需要協助的項目寫清楚需要誰做什麼。
- 常見錯法：照時間順序寫成工作流水帳，讀者找不到要他決定的事。

## 事件報告

讀者要了解事件經過、影響與後續行動，焦點放在系統與流程，不放在個人（[Google SRE: Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)）。

- 開頭：發生什麼、影響範圍與期間、目前狀態。
- 時間線：絕對時間並標時區，三件以上用表格。
- 原因：事實直接講，推論在當句標「推測」，排除的假設條列，不逐段展開。
- 處置與行動項目：每項寫 owner 與期限，owner 未知就標「待指派」，不猜。
- 常見錯法：把調查過程的查詢與逐行程式碼放進報告。這些屬於查證用的部分或另存。
