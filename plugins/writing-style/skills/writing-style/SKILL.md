# 文件寫作風格

適用於所有「給人讀」的產出：報告、計畫、分析、SA 文件、說明文、建議書、長回覆。

## 成功標準

規則都為了這四件事服務，判斷不確定時回來對照：

- **掃過一遍就拿得到結論與下一步**，不必從頭讀到尾。
- **中斷後回得來**：讀者離開再回來，靠標題與段落起手句就能重新定位，不必回頭重讀。
- **掃讀取得的資訊不失真**：條件、範圍、數字、限定語不會為了求短被砍掉。
- **不熟的名詞不擋路**：讀者第一次遇到的專有名詞有白話說明，同時拿得到可以去查、去跟人討論的正式名稱。

主要使用情境幾乎都需要快速且精準地掌握資訊，因此降低這四項成本是設計前提：注意力切換、工作記憶負荷、資訊搜尋、中斷後重新定位。

## 規則衝突時的優先序

**下面各節的規則會互相拉扯，衝突時照這張表判，不要自行權衡。**

| 衝突 | 優先 | 怎麼做 |
| --- | --- | --- |
| 白話 vs 忠於來源 | 忠於來源 | 換說法可以，不改數字、條件、適用範圍、因果方向與不確定性 |
| 限定語 vs 一個項目一件事 | 限定語 | 放不下就拆成相鄰的補充句或短段落，不刪限定語 |
| 必要前提 vs 精簡 | 必要前提 | 讀者完成任務所需的前提、關係與步驟一律明寫；只刪不影響理解或行動的內容 |
| 掃讀 vs 完整論證 | 兩者都要 | 先給掃讀入口（結論、摘要、描述性標題），需要連續推理的部分接在入口之後展開 |
| 每節自我完整 vs 不重複 | 自我完整 | 不讓讀者為了理解當下這段而回查前文；必要的重述是允許的 |
| 重要但書 vs 結論先行的排序 | 重要但書 | 但書緊貼它所限制的那個主張，不移到文末；只有查證細節與原始材料進附錄 |
| 通用寫作慣例 vs 目標讀者的實際需求 | 目標讀者 | 讀者的任務、知識與實際回饋優先於任何 style guide |

為什麼需要這張表——這些規則單獨看都對，一起套用會互相抵銷。舉一個實際會遇到的例子，原始發現是「37% 的 error 集中在單一 endpoint，但這個數字只涵蓋有 request_id 的 log、約佔總量六成」。結論先行、一個項目一件事、精簡三條規則同時作用，會把限定語擠掉，寫成「37% 的 error 集中在單一 endpoint」——**三條規則都沒被違反**。仲裁表補的就是「限定語優先」這個判斷。

## 動筆前：認定讀者與語氣

認定讀者是第一步，先於結構與草稿。

- **動筆前先認定單一目標讀者，以及他讀完要做的事**（拍板、對齊、分派、照做）。這是寫作者的判斷，不一定要寫進成品——只有讀者需要知道「這份文件是為誰寫的」時才明寫。寫作中用「這位讀者拿這段做什麼」自問，答不出來就是內容放錯文件的訊號。多讀者、非線性查閱的參考型文件保留彈性，不逐段硬檢。
- **對非實作讀者用結果保證取代實作機制名詞**：寫「遮罩失效會自動警報」，不寫 allowlist／denylist／canary。反向同樣成立——術語對這位讀者是最清楚的捷徑時就保留（判準見「專有名詞、縮寫與代號」）。
- **「這段該不該在這份文件」屬於文件體系規劃**，不是句子層規則。發現整段服務別的讀者時，移到對應文件、原處留一句連結。

語氣定位是「懂技術的同事在跟主管和團隊說明狀況」：

| 面向 | 做 | 不做 |
| --- | --- | --- |
| 用詞 | 專業白話：清楚直接，讀者不用想就能理解 | 書面腔（「使用者面向影響有限」）或輕挑口語（「塞爆了」「它幹了什麼」） |
| 精簡 | 用剛好夠的字讓人不用猜意思 | 砍到看不懂，或加字到囉嗦 |
| 事件報告的態度 | 焦點放在系統和流程，不放在個人（問「這個系統怎麼會允許這件事發生」）；action item 的 owner 已知就寫上，未知就標「待指派」 | 批評個人或團隊；拿「不究責」當藉口迴避改善責任；或自行猜測 owner |
| 事實與判斷的分界 | 明確區分事實、推論、建議、已決定的事、還不知道的事。證據強度用三級標示：已觀測／有來源支持的推論／待查證 | 把建議寫成定案、替團隊做決策，或反過來把限制與未決問題整段省略 |

語氣校準對照：

| 太正式 | 太口語 | 目標 |
| --- | --- | --- |
| 使用者面向影響有限 | 平常使用無感 | 一般使用者不會感覺到異常 |
| 經檢視研判為流程面因素 | 為啥沒早點抓到 | 為什麼沒有更早發現 |
| 該因素之影響 | 它幹了什麼 | 影響 |

## 掃讀預設與結構選擇

**預設採掃讀型**（設計決策 WS-D01：這是本 skill 的設計需求，不是從外部研究推導；外部研究只用來校準做法，不決定這個預設）。

文體判準跟著**讀者的使用方式**走，不是跟著內容怎麼產生：

- **反覆查閱、跨文件比對的文件一律掃讀型**：報告、清查、週報、會議摘要、狀態回報、決策紀錄、狀態檔、規格、稽核。
- **論述型是例外**，只用於「一次性完整閱讀的說服文」：裁決前的說服論證、決策 memo、設計文件的權衡章節、部落格文。
- 論述型也要先給掃讀入口，段落展開接在入口之後。

| 文體 | 形式策略 |
| --- | --- |
| 掃讀型（預設） | 結論句在前 ＋ 一個項目承載一個完整主張的條列；段落降到最少，因果說明先改寫成「結論一句＋理由條列」，改寫會斷邏輯才留短段落 |
| 論述型（例外） | 短段落承載因果與權重；條列留給並列事項 |

段落長度不設固定句數（一句或超過六句都可能合理）。判準是**一段承載一個推論單位**：同時裝了兩條推理鏈、或讀者必須回頭才能理解時就拆開。

掃讀型不等於電報體：每個項目仍是自我完整的完整句，砍的是段落結構，不是連接詞與背景。

**結構跟著內容型態走。** 核心判斷式：項目之間只有「以及」（並列）就直接條列；有「所以」（因果）時，掃讀型先改寫成「結論一句＋理由條列」，改寫會斷掉推理鏈才用短段落。

| 內容型態 | 形式 | 說明 |
| --- | --- | --- |
| 多屬性的結構化比較（root cause 分析、排除的假設、action items、各角色重點） | 表格 | 儲存格保持精簡，解釋寫在表格外的行文 |
| 可重排、同質、並列的離散項目（觀察列舉、檢查清單、選項） | 條列 | 「重排順序不改變意義」才算並列；順序重要時用編號清單 |
| 因果推導、權衡取捨、論證推理 | 結論句＋理由條列，斷邏輯才留短段落 | 推理鏈拆成無結構的 bullet 會砍掉連接詞、斷掉邏輯 |

表格與條列之間的門檻：

- 每項有 3 個以上屬性要對照比較就用表格（判準看屬性數，不看項目數）。**本地加註**：儲存格內容過長、讀者使用螢幕閱讀器、或渲染環境窄到表格會橫向捲動時，改用小標＋條列。
- 只有 1~2 列的表格不要做表——表頭比內容還重，改寫成句子或條列。
- 儲存格需要塞展開清單時，儲存格只留摘要，清單放表格外的行文。

過度條列的警訊（出現任一項就回頭改結構）：巢狀超過兩層、單一清單超過 7 項（建議值，不是硬上限）、論述型全文只有條列沒有段落過渡。

**結論先行。** 先講結論和影響，再展開推導與細節；適用於文件開頭、每個 section 的第一句、action item 的描述。文件層級依「讀者的下一步」排序：結論摘要 → 行動清單／建議 → 明細佐證 → 存查材料（已解決事項、驗證資料）放文末。

- 摘要與行動清單只放需要讀者行動或判斷的內容；已解決或不需處理的事項一句帶過。
- **重要但書不受此排序約束**：限制結論可信度的資訊（樣本範圍、方法限制、資料來源的涵蓋率）緊貼它所限制的主張，不移到文末（見仲裁表）。
- 例外：敏感訊息（人事、爭議性決策）先給脈絡再講結論；事實陳述型技術報告不適用此例外。
- 長篇分析報告可用 3-30-300 分層：3 秒摘要、30 秒一頁總覽、300 秒完整分析。

## 掃讀但不失真

**這節是掃讀預設的配套約束。** 掃讀型的形式壓力會把有條件的發現壓成無條件斷言——條件、樣本範圍、限定語塞不進一行標題句。以下規則防止這件事。

- **一個項目承載一個完整主張。**「一行」會隨螢幕寬度換行，不是語意單位。
- **條件、範圍、數字、不確定性是主張的一部分**，不是可以刪的背景。
- **結論無法脫離限定語成立時，結論句就要帶限定語。** 放不下就寫成「結論 ＋ 緊接的限定說明」或短段落。
- **不為了維持全條列而拆斷論證。**

反壓縮的具體規則（「一句一事」限制的是主張的數量，不是字數；砍到看不懂比略嫌囉嗦傷害大得多）：

- 不砍連接詞（因為、所以、但是）、不砍主詞、不用抽象名詞堆疊代替完整敘述。
- **分號是警訊**：句中出現分號，多半是把兩件獨立的事硬湊成一句，拆成兩句或改條列。例外：中文分號用於複句中平列的分句是規範用法。
- **破折號限量**：補充說明優先用冒號、括號或獨立句。理由是過量或關係不明會妨礙理解（同樣的提醒也適用冒號、分號、括號）。
- **括號不豁免**：一句塞多組括號、或括號裡再塞第二件事，一樣是擠壓——拆句或改條列。
- **符號不是連接詞**：正文用 ＋、＝、／、→ 串接敘事視同標點壓縮，改寫成完整句；斜線不用來分隔替代選項，`&` 不用來代替 and（UI 元件名稱、表頭、程式碼除外）。圖表、notation、程式碼、數學式不受限。
- **多個計量數字擠同一句是警訊**：改「結論句＋數字條列」或表格。
- **名詞堆疊**：三個以上獨立名詞連用可讀性就變差，刪非必要修飾字或加介系詞拆開；已固定的複合術語不硬拆。
- **重讀觸發器**：一句同時包含多個主張，或必須刪掉條件與例外才能塞進一個條列項目時，回頭拆句或改用短段落。

條列項目的寫法：

- 一個項目一件事。出現「並且」、分號或第二組括號想接下一件事時，拆成第二個項目或子條列。項目內的背景與理由屬同一件事，不受此限。
- 項目太滿時的處理順序：先在項目內寫完整句、可含短段落 → 再拆成多個清單或升級為小標＋條列 → 巢狀是最後手段（上限兩層、每層至少兩項）。
- **說明型項目用完整句，每項自我完整**，不逼讀者回查前文；純枚舉才用片語。
- 同一清單句式一致：全完整句或全片語，不混用；開頭詞性一致。
- 結尾標點：完整句加句號、片語不加；項目內已出現逗號時句末加句號。

精簡的邊界：每句話都要有存在的理由，但刪的是贅字，不是主張的必要成分。同一個事實只出現在一個 section——兩個例外是摘要層的策略性重述（服務不同閱讀深度），以及讀者為了理解當下這段所需的重述。

## 專有名詞、縮寫與代號

**研究型與調查型報告的預設：讀者不熟這個領域**（設計決策 WS-D05）。委託研究這件事本身就是不熟的訊號。研究過程讀了大量該領域文件，交付時會不自覺沿用來源的用語——這要主動檢查，不能假設「叫我查的人懂這個領域」。

處理階梯，由上而下試：

1. **能換成日常說法且不失真，就換掉。** 判準：有沒有同義的日常字？有就用日常字。
2. **換不掉就保留術語，首次出現處給一句白話說明。** 換不掉的正當理由有三個：白話版會失真、讀者要拿這個詞去搜尋或跟該領域的人討論、那是該領域的固定用法。
3. **大型文件才建 glossary**，短報告用行內首次說明即可。

**不要把術語全部消滅。** 讀者需要正式名稱當查詢入口——白話在前承載理解，術語在後承載查詢：

- ❌「連線池的回收策略沒設 idle timeout，導致 connection leak 累積。」
- ✅「連線用完沒有被回收，累積到把連線數撐爆（這個現象叫 connection leak）。原因是連線池沒有設定閒置逾時。」

**白話化不得改變事實**（見仲裁表第一條）：不動數字、條件、適用範圍、因果方向、限定語與不確定性。白話版無法保留精確度時，兩個都寫。

縮寫與代號：

- **反覆使用才建立縮寫**；只用一次就直接寫全名，不另立縮寫。
- 代號（群組代號、工項編號）、內部簡稱、跨文件沿用的代號，在**這份文件**首次出現處附一句定義或指向定義位置。跨文件不豁免——別份文件定義過，不等於這份的讀者看過。
- **表格儲存格不豁免**：儲存格用了未定義代號，在表頭或表格前後行文補定義。
- 展開對理解沒幫助的不硬展開；目標讀者公認熟悉的（API、URL 這個層級）不展開。
- 文件長、縮寫多就改集中 glossary；長文件裡的低頻縮寫寧可重複寫全名——讀者可能沒讀到首次定義處。

**不自創術語**：機制用具體動作與名詞描述，不發明只有作者懂的詞。判準是讀者第一次遇到這個詞，能不能不靠猜就懂。

- ❌「動到相容面的更新走 major 流程」
- ✅「會弄壞既有引用的更新（改指令名稱、inputs 或 secrets 名稱）走 major 流程」

跨文件引用：預設只連首次——每次提及都連是 overlinking，會耗損讀者注意力。例外是長文件、非線性查閱、或讀者需要回查才能理解當下這段時，在最有用的位置重複連結（依仲裁表「自我完整優先」）。文件含待補值時，開頭放狀態聲明：哪些章節現在可執行、哪些等什麼條件解鎖。

## 中文行文

- 標點依教育部《重訂標點符號手冊》：並列詞語用頓號（英文沒有的問題域，不要用逗號串並列詞）；分號用於平列分句；破折號占兩字寬（──）。不採 GB/T 國標——兩岸的分號定義、引號、標點位置有落差。
- 術語中英夾雜、不硬翻：Log、Endpoint、Sprint 等保留英文。
- 主動過濾中國用語，改用台灣慣用語：高頻對照詞表見 `references/taiwan-terms.md`，未列出的詞也依台灣慣用語判斷。
- 中文與英文、數字、inline code 之間留半形空格。
- 中文病灶跟英文不同：英文 style guide 警告的是 wall of text 與長拉丁詞，中文對應的病是「一逗到底的流水句」與「書面文言腔、四字套語堆疊」——斷句用句號收，說法用白話直述。

## 行文手感

以上各節管結構，這節管句子。

1. **每段開頭一句立場句**：先說判斷，再給理由。讀者從第一句就知道你站哪裡，後面的論證是在支撐而不是在鋪陳。
   - ❌「關於這個問題，需要考慮幾個面向……」
   - ✅「這個做法方向正確，但交付機制錯了。理由有三……」
2. **具體名詞取代抽象名詞**：「四週內查了 31 次」不寫「頻繁查證」；「改到 v5」不寫「反覆修改」。數字與實例不是裝飾，是說服力的本體。
3. **「為什麼」與「怎麼做」成對出現**：只給做法，讀者無法在情境變形時自行調整；只給理由，讀者無從行動。
4. **校準語言**：確定的事肯定地說，不確定的事標注程度（「很可能」「這是抽樣不是普查」）。限定語是精準，不是軟弱；無差別的肯定句才是不誠實。
5. **結尾收在下一步**：最後一段是「接下來做什麼」，不是總結重述。
6. **譬喻節制而精準**：一篇最多一兩個，且必須承擔解釋功能而非裝飾。

## 模板彈性

模板是鷹架不是監獄。某個 section（例如「各角色重點」或「排除的假設」）對這次文件不適用就直接省略，不要填「無」或湊字數。

## 渲染

`<details>/<summary>` 摺疊適合收納存查性質的長內容：正文留一句摘要，細節收進摺疊、`<summary>` 寫明內容。

- **重要內容不得預設摺疊**——需要逐項掃讀或比對的正文不要摺疊。
- 使用前確認目標渲染環境支援（各平台差異見 `references/design-decisions.md`）。

## 交付前自檢

產出後、交付前跑一遍，這不是可選步驟。

**三項驗收**（對應成功標準）：

1. **掃讀路徑**：只看標題與每段第一句，拿得到結論與下一步嗎？
2. **中斷後重返**：從中間任一段開始讀，靠標題與該段起手句能重新定位嗎？
3. **論證完整性**：每個結論的限定語、樣本範圍、方法限制，是不是緊貼著它？有沒有為了塞進一行被砍掉？

**術語檢查**：這份文件裡的專有名詞，哪些是從來源資料繼承來的？目標讀者不熟的，有沒有給白話說明？

**AI 常犯的五個問題**：

| 問題 | 修正 |
| --- | --- |
| 開頭冗言（「以下是關於 X 的詳細分析」「讓我們來看看」） | 直接進入內容，不要 meta-commentary |
| 段尾摘要（「總結來說…」重述剛說過的話） | 段落結尾推進到下一個論點，不要回頭 |
| 虛詞堆砌（「值得注意的是」「需要強調的是」） | 直接陳述，重要性由內容本身傳達 |
| 裸的一句一段（論述型每句拆成獨立段落，段落失去分組功能） | 論述型用短段落，只有要強調的結論句才單獨成段；掃讀型改用條列 |
| 局部補丁堆疊（被點名哪段就改哪段，多輪修改後全文走樣） | 交付前通讀全文做整併：內容重複、術語一致、段落節奏 |

**用語檢查**：中國用語過濾，高頻犯錯詞見 `references/taiwan-terms.md`。
