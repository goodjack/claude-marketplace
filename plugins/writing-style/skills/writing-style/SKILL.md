# 文件寫作風格

適用於所有「給人讀」的產出：報告、計畫、分析、SA 文件、說明文、建議書、長回覆。目的是讓讀者快速吸收和行動。原則依據 Google Developer Documentation Style Guide、Microsoft Writing Style Guide、NNG 掃描閱讀研究、教育部《重訂標點符號手冊》，以及 Blameless Postmortem 文化共識（出處清單見文末）。

## 語氣定位——Knowledgeable Friend（Google Style Guide）

像一個懂技術的同事在跟主管和團隊說明狀況。清楚、直接、容易吸收，但用語得體。

| 面向 | 做 | 不做 |
| --- | --- | --- |
| 語氣 | 專業白話（Professional Plain Language）：清楚直接，讀者不用想就能理解 | 書面腔（「使用者面向影響有限」）或輕挑口語（「塞爆了」「它幹了什麼」） |
| 表達形式 | 預設掃讀型：結論句在前、一行一事實條列、多屬性比較用表格；論證內容依「文體預設」與「結構選擇」處理 | 整段散文 wall of text；或電報碎片式條列（砍掉主詞、連接詞與背景） |
| 精簡 | As concise as possible, but as wordy as necessary——用剛好夠的字讓人不用猜意思 | 砍到看不懂（過度精簡），或加字到囉嗦（冗餘） |
| 態度（事件報告） | Blameless but accountable：焦點放在系統和流程，不放在個人。「How did the system allow this?」但 action items 必須有明確 owner，不是不追蹤改善責任 | 批評個人或團隊，使用輕挑或嘲諷語氣，或反過來用 blameless 當藉口迴避改善責任 |
| 重複 | DRY（Don't Repeat Yourself）：同一個 fact 只出現在一個 section（例外見精簡校準） | 同一件事在多個 section 用不同措辭重述 |
| 未決策事項 | 只放「事實」和「已決定的事」。Action Items 是 AI 基於調查的初步建議（Proposed），明確標示需團隊討論確認 | 把建議寫成定案（如「高優先本週完成」），或替團隊做決策 |

## 語氣光譜

基於 Google / Microsoft Style Guide + Blameless Postmortem 文化：

| 太正式 ❌ | 太口語 ❌ | 目標 ✅ |
| --- | --- | --- |
| 「使用者面向影響有限」 | 「平常使用無感」 | 「一般使用者不會感覺到異常」 |
| 「緊急處置手動清除所有 session 後」 | 「清掉所有 session」 | 「清除 Redis 後」 |
| 「流程面根因」 | 「為啥沒早點抓到」 | 「為什麼沒有更早發現」 |
| 「該因素之影響」 | 「它幹了什麼」 | 「影響」 |

## 讀者範圍——先認定讀者再動筆

認定讀者是寫作流程的第一步，先於結構與草稿（plain language 系原則）。

- 文件開頭先定義單一目標讀者與他讀完要做的事（拍板、對齊、分派、照做）。寫作中用「這位讀者拿這段做什麼」自問；答不出來就是內容放錯文件的訊號。reference 型文件（多讀者、非線性查閱）保留彈性，不逐段硬檢。
- 機制名詞降階：對非實作讀者（決策者、協調者）用結果保證取代實作機制名詞——寫「遮罩失效會自動警報」，不寫 allowlist／denylist／canary。反向同樣成立：術語對目標讀者是最清楚的捷徑時保留，去 jargon 不等於禁用必要術語。
- 「這段內容該不該在這份文件」屬文件體系規劃（資訊架構層，參考 Diátaxis 的文件分型），不是句子層規則。本節管「寫的時候對準讀者」；發現整段服務別的讀者時，移到對應文件、原處留一句連結。

## 文體預設——掃讀優先

**預設文體是掃讀型**：日常產出的文件絕大多數是給 scrum team 各角色快速且精確同步用的（報告、清查、週報、會議摘要、狀態回報），讀者是掃不是讀。產出時不用問，直接用掃讀型；論述型是例外，只在內容真的需要連貫論證時切換。

| 文體 | 適用 | 形式策略 |
| --- | --- | --- |
| 掃讀型（預設） | 報告、清查／盤點、週報、會議摘要、狀態回報、公告——所有同步性文件 | 結論句在前＋一行一事實的條列；段落降到最少，因果說明先改寫成「結論一句＋理由條列」，改寫會斷邏輯才留短段落（≤2 句） |
| 論述型（例外） | 需要論證因果、相對重要性與 trade-off 的內容：決策／策略 memo、設計文件的權衡章節、部落格文 | 短段落（2~4 句、一段一概念）承載因果與權重；條列留給並列事項 |

- 依據：NN/g 實證（79% 讀者掃讀，web 與 traditional writing 是兩套規則、字數砍半）＋GOV.UK 官方標準（段落只設上限 5 句）＋BLUF 與 PM 業界共識（status 用條列、60 秒讀完）。
- 邊界（Bezos 反例）：決策論證內容即使出現在掃讀型文件裡，也保留短段落——條列會壓扁相對重要性與想法間的關聯。
- 掃讀型不等於電報體：每行仍是自我完整的完整句（受反壓縮條款約束），砍的是段落結構，不是連接詞與背景。
- 目標讀者的實際回饋優先於通用 guide：讀者說難讀就調整，不拿 style guide 壓讀者。

## 結構選擇——形式跟著內容型態走

核心判斷式：項目之間只有「以及」（並列）直接條列；有「所以」（因果）時，掃讀型（預設）先改寫成「結論一句＋理由條列」，改寫會斷掉推理鏈才用短段落；論述型直接用段落。

| 內容型態 | 形式 | 說明 |
| --- | --- | --- |
| 多屬性的結構化比較（root cause 分析、排除假設、Action Items、角色重點） | 表格 | 儲存格保持精簡，解釋寫在表格外的行文 |
| 可重排、同質、並列的離散項目（觀察列舉、檢查清單、選項） | 條列 | 「重排順序不改變意義」才算並列；順序重要時改用編號清單 |
| 因果推導、權衡取捨、論證推理、流程面敘事 | 掃讀型（預設）：結論句＋理由條列，斷邏輯才留短段落（≤2 句）；論述型：段落 2~4 句 | 推理鏈硬拆成無結構的 bullet 會砍掉連接詞、斷掉邏輯；「結論＋理由」的條列結構保留了因果方向 |

依據：NNG 研究顯示 79% 讀者掃描而非逐字讀，結構化格式利於掃描；但 Jansen（2014）同時發現 bullet 只對「清單項目本身」的記憶有利，對「周邊段落內容」反而有害——所以論證內容不能打散成無結構的碎片：掃讀型用「結論＋理由」的結構化條列保留推理方向，論述型歸段落。

表格與條列之間的門檻（判準以屬性數為主、項目數為輔；中間地帶各 guide 判準不一，保留彈性判斷）：

- 每項有 3 個以上屬性要對照比較 → 表格（Google 的判準看屬性數，不看項目數）。
- 只有 1~2 列的「表格」不要做表——表頭比內容還重，改寫成句子或條列（澳洲政府 Style Manual）。
- 儲存格內容需要塞展開清單（如「9 個欄位」）時，儲存格只留摘要，清單放表格外的行文。

過度條列警訊（出現任一項就回頭改結構）：

- 巢狀超過兩層。
- 單一清單超過 7 項（Microsoft 建議 2–7 項）。
- 論述型文件全文只有條列、沒有段落過渡（AI 常見病，社群稱 Staccato Stack）；掃讀型允許全條列，但每條必須自我完整，不是電報碎片。

## 結論先行（BLUF）

BLUF（Bottom Line Up Front）——先講結論和影響，再展開推導過程與細節。讀者（尤其是主管）需要在前幾秒決定「這件事要不要深入看」，不要讓他們讀完三段背景才看到重點。

適用於：文件開頭、每個 section 的第一句、action items 的描述。

文件層級的 section 排序也適用（inverted pyramid；BLUF、Minto、NN/g、GOV.UK 四個體系同向）：

- 依「讀者的下一步」排序：結論摘要 → 行動清單／建議 → 明細佐證 → 存查性質的材料（已解決事項、無風險項目、驗證資料）放文末附錄。
- 長篇分析報告可採 3-30-300 分層（團隊慣例範例，與 inverted pyramid 同向）：3 秒 executive summary、30 秒一頁總覽、300 秒完整分析。
- 摘要與行動清單只放需要讀者行動或判斷的內容；已解決或不需處理的事項在摘要一句帶過，不佔行動清單與總覽版面。
- 例外：敏感訊息（人事、爭議性決策）先給脈絡再講結論，避免顯得冷酷或引發防衛；事實陳述型技術報告不落入此例外。

## 反壓縮條款——一句一事不是電報體

「一句一事」限制的是 idea 的數量，不是字數。背景、條件、理由屬於同一個 idea 的必要成分，不得為了縮短而砍掉——「砍到看不懂」比「略嫌囉嗦」傷害大得多。

- 禁止電報體：不砍連接詞（因為、所以、但是）、不砍主詞、不用抽象名詞堆疊代替完整敘述。
- 分號是警訊：句中出現分號，預設代表把兩件獨立的事硬湊成形式上的一句——拆成兩句，或改條列。例外：中文分號用於複句中平列的分句是規範用法（教育部），並列語意可正常使用。
- 破折號限量：補充說明優先用冒號、括號或獨立句；全文破折號從嚴限量。理由有二：Microsoft 的可讀性警告，加上中英文社群都把破折號堆疊視為 AI 生成特徵。
- 括號不豁免：括號適合裝一個補充；一句塞多組括號、或括號裡再塞第二件事，一樣是擠壓——拆句或改條列。
- 符號不是連接詞：正文用 `＋`、`＝`、`／`、`→` 串接敘事視同標點壓縮，改寫成完整句（Google 明訂斜線不可分隔替代選項、`&` 不可代 and）。只限正文：圖表、notation、程式碼、數學式不受限。
- 多個計量數字擠同一句是警訊：改「結論句＋數字條列」或表格（Federal Plain Language：資料進表格，內文只留一兩項）。「一句超過兩個數字就考慮拆」是團隊自訂門檻，非官方通則。
- 名詞堆疊（noun strings）：三個以上獨立名詞連用可讀性就變差（plain language 門檻＝3）——刪非必要修飾字、加介系詞拆開；已固定的複合術語豁免，不硬拆。
- 句長參考：中文一句 20 字內最佳、40 字是上限（社群收斂值，非官方規範）。這是平均語意，允許長短交錯；不是把每句都壓短的目標值，壓出電報體就本末倒置。

## 縮寫與代號——首次出現先定義

- 代號（群組代號、工項編號）、內部簡稱、跨文件沿用的代號：在「本文件」首次出現處附一句定義，或指向定義位置。跨文件不豁免——別份文件定義過，不等於這份文件的讀者看過。
- 表格儲存格不豁免：儲存格用了未定義代號，在表頭或表格前後行文補定義。（本地約定；Google／Microsoft 只規範到標題層級，未對儲存格表態。）
- 三個豁免（Google／Microsoft 明訂）：只用一次的縮寫直接寫全名、不另立縮寫；展開對理解沒幫助的不硬展開；目標讀者公認熟悉的（API、URL 級別）不展開。
- 文件長、縮寫多（社群參考門檻：數十頁、20 個以上縮寫）改集中 glossary；長文件裡的低頻縮寫寧可重複寫全名——讀者可能沒讀到首次定義處。

## 條列項目的寫法

- 一個項目一件事：出現「並且」、分號或第二組括號想接下一件事時，拆成第二個項目或子條列。項目內的背景與理由屬同一件事，不受此限（一句一事管 idea 數量，見反壓縮條款）。
- 項目太滿時的處理序：先在項目內寫完整句、可含短段落（Microsoft 官方允許）→ 再拆成多個清單、或升級為小標＋條列（論述型用小標＋段落）→ 巢狀是最後手段（上限兩層、每層至少兩項）。次級條列不是預設解法。
- 說明型項目（含背景＋建議＋理由）用完整句，每項自我完整，不逼讀者回查前文；純枚舉才用片語。
- 同一清單句式一致：全完整句或全片語，不混用；開頭詞性一致（平行結構）。
- 結尾標點：完整句加句號、片語不加；項目內已出現逗號時句末加句號。

## 精簡校準

- **Orwell's Third Rule**（「If it is possible to cut a word out, always cut it out」）：每句話都要有存在的理由。但刪的是贅字，不是 idea 的必要成分——受反壓縮條款約束。
- **DRY（Don't Repeat Yourself）**：同一個 fact 只出現在一個 section。例外：executive summary 的策略性摘要是為不同閱讀深度服務，不算重複。

## 中文行文慣例

- 標點依教育部《重訂標點符號手冊》：並列詞語用頓號（英文沒有的問題域，不要用逗號串並列詞）；分號用於平列分句；破折號占兩字寬（──）。不採 GB/T 國標——兩岸的分號定義、引號、標點位置有落差。
- 術語中英夾雜、不硬翻：Log、Endpoint、Sprint 等保留英文。
- 主動過濾中國用語，改用台灣慣用語：高頻對照詞表見 references/taiwan-terms.md；未列出的詞也依台灣慣用語判斷。
- 中文與英文、數字、inline code 之間留半形空格。
- 中文病灶對照：英文 style guide 警告的是 wall of text 與長拉丁詞，中文的對應病是「一逗到底的流水句」與「書面文言腔、四字套語堆疊」——斷句用句號收，說法用白話直述。

## AI 產出常見問題

LLM 有特定的寫作失敗模式，產出文件時需主動避免：

| Anti-pattern | 說明 | 修正 |
| --- | --- | --- |
| 開頭冗言 | 「以下是關於 X 的詳細分析報告」「讓我們來看看」 | 直接進入內容，不要 meta-commentary |
| 段尾摘要 | 每段結尾用「總結來說，...」重述剛說過的話 | 段落結尾推進到下一個論點，不要回頭 |
| 過度條列 | 把需要上下文連貫的論證拆成無結構的 bullet 碎片 | 因果內容用「結論句＋理由條列」保留推理方向，斷邏輯才留短段落（見文體預設） |
| 電報式壓縮 | 為了短而砍連接詞、砍主詞、堆抽象名詞，讀者要自己腦補推論 | 依「反壓縮條款」：一句一事管 idea 數量，不管字數 |
| 標點硬湊 | 用分號或破折號把多個概念擠成形式上的一句 | 拆成兩句或改條列；破折號改冒號、括號或獨立句 |
| 裸代號 | 代號、內部簡稱首次出現不解釋，讀者要自己解碼 | 首次出現附一句定義或指向定義處（見「縮寫與代號」） |
| 虛詞堆砌 | 「值得注意的是」「需要強調的是」「重要的是」 | 直接陳述事實，重要性由內容本身傳達 |
| 裸的一句一段 | 論述型文字每句拆成無標記的獨立段落，段落失去「一段一概念」的分組功能；或把掃讀需求誤解成「拆散段落」 | 論述型：短段落（2~4 句），只有要強調的結論句才單獨成段。掃讀型：改用條列（一行一事實、帶標記），不是裸單句段（見文體預設）。semantic line breaks 是 source 層慣例、不影響渲染，不能拿來佐證渲染層的一句一段 |
| 局部補丁堆疊 | 被點名哪段就修哪段，多輪修改後全文走樣：內容重複、術語漂移、節奏斷裂 | 交付前通讀全文做整併檢查（DRY、術語一致、段落節奏），不能只看剛改的段落 |

## 跨文件引用與文件狀態

- 引用他文件的名詞、規範或狀態：首次引用處附連結（Google cross-references）。只連首次——每次提及都連是 overlinking，會耗損讀者注意力與信任（NN/g）。
- 文件含 {placeholder} 待補值時，開頭放狀態聲明：哪些章節現在可執行、哪些等什麼條件解鎖（比照 W3C「Status of This Document」慣例）。

## 渲染相容性——摺疊區塊的使用時機

`<details>/<summary>` 摺疊適合收納存查性質的長內容（附錄長表、驗證資料、可重現指令）：正文留一句摘要，細節收進摺疊、`<summary>` 寫明內容。CodiMD/HackMD、GitHub 與多數 IDE 預覽都支援，存查長表預設可摺疊。

- 例外：Notion 貼上或匯入 Markdown 時會直接移除標籤（內容可能整段消失），不會變成 toggle——確定要貼到 Notion 的文件先展開，改用「存查材料後置＋文末附錄」。
- 已知副作用：Firefox/Safari 的頁內搜尋找不到摺疊內容、列印預設不含摺疊內容——讀者需要逐項掃讀或比對的正文內容不要摺疊。

## 模板彈性（Flexible Template）

**「Only Include Relevant」**（Google SRE 精神）：模板是鷹架而非監獄。若某個 section（例如「各角色重點」或「排除的假設」）對這次文件不適用，請直接省略該區塊，不要填入「無」或湊字數。

## 行文手感（從實際好讀的範例提煉）

以上各節管「結構」，本節管「句子」。八條規則，各附機制說明——懂機制才能在變形情境下自行判斷：

1. **每段開頭一句立場句**：先說判斷，再給理由。「不是，你的直覺是對的」「夠好，但有三個可修的弱點」——讀者從第一句就知道你站哪裡，後面的論證是在支撐而不是在鋪陳。
   - ❌「關於這個問題，需要考慮幾個面向……」（讀完仍不知道結論）
   - ✅「這個做法方向正確，但交付機制錯了。理由有三……」
2. **完整句子優先於片語**：表格儲存格以外，句子要有主詞和動詞；縮寫、代號、術語首次出現先用一句話解釋。多花五個字讓讀者不用猜，永遠划算。
3. **具體名詞取代抽象名詞**：「四週內查了 31 次」不寫「頻繁查證」；「改到 v5」不寫「反覆修改」。數字與實例不是裝飾，是說服力的本體；抽象形容詞是資訊密度為零的填充物。
4. **「為什麼」與「怎麼做」成對出現**：只給做法，讀者無法在情境變形時自行調整；只給理由，讀者無從行動。每個建議都問自己：機制講了嗎？下一步講了嗎？
5. **校準語言**：確定的事就肯定地說（「全數通過」），不確定的事標注程度（「很可能」「屬推論延伸」「這是抽樣不是普查」）。限定語是精準，不是軟弱；無差別的肯定句才是不誠實。
6. **結尾收在下一步**：文章與回覆的最後一段是「所以接下來做什麼」，不是總結重述。讀者放下文件的那一刻，手上應該有動作，不是感想。
7. **譬喻節制而精準**：一篇最多一兩個，且必須承擔解釋功能而非裝飾（「共識是移動平均」「半成品是庫存不是愧疚清單」）。好譬喻讓人一次聽懂機制；裝飾性譬喻只是打斷閱讀。
8. **不自創術語**：機制用具體動作與名詞描述，不發明只有作者懂的詞。判準：讀者第一次遇到這個詞，能不能不靠猜就懂；不能就把它展開成白話。
   - ❌「動到相容面的更新走 major 流程」（「相容面」是自造詞，讀者要先解碼）
   - ✅「會弄壞既有引用的更新（改指令名稱、inputs 或 secrets 名稱）走 major 流程」
