# 產出報告

報告目標讀者涵蓋前端、後端、Tech Lead、SRE、TPM、主管，乃至外部協作團隊，各方對系統背景的了解程度不一。報告的目的是讓多方**一次讀懂來龍去脈並知道下一步**，不是交代責任。因此：
- 技術細節（程式碼、查詢語法）可以簡單解釋，不用預設讀者一定懂
- 系統架構說明是幫讀者找出「這東西在哪」，不是在界定誰該負責
- 程式碼位置標籤不加「後端同仁參考」之類的觀眾限定語；任何需要了解的人都可以看

此模板是內建事件報告格式。若專案有固定欄位、嚴重度定義、issue tracker 或 owner 標記方式，沿用實際慣例。

**每個數據點必須附查詢來源編號（見 `references/analysis-principles.md` 的「數據點附查詢來源」章節）。**

輸出路徑：`reports/YYYY-MM-DDTHHMM.md`，存放於專案根目錄的 `reports/` 目錄。

圖表路徑：`reports/assets/YYYY-MM-DDTHHMM/`，與報告檔名對應。產圖方式見 `references/metrics-charts.md`。

報告有兩種類型，依入口和情境選擇：
- **定期掃描報告**（入口 A）：週報 / 健檢，展開 P1/P2 六面向
- **事件報告**（入口 B / 特定問題調查）：四層 Progressive Disclosure（Executive Card → 事件總覽 → 跨團隊影響 → 技術細節），主管 30 秒掌握結論、Tech Lead 5 分鐘了解全貌、工程師讀完整技術脈絡

## 通用撰寫原則（兩種報告都適用）

### 數據與來源

- 每個數據點附查詢來源編號（`[Q1]`、`[ALB-Q1]` 等），讓讀者能自行驗證（詳見 `analysis-principles.md`「數據點附查詢來源」）
- 不同觀測層的數據標明來源：後端 application log ≠ CDN access log ≠ ALB access log，不混在同一行
- 語言精準：資料有混合結果時用限定語，不用絕對語句（詳見 `analysis-principles.md`「語言精準」）
- 行動清單每行有 Owner + 優先序；Owner 標「團隊/角色」而非個人名字
- 涉及基礎設施指標的問題，附 CloudWatch 圖表（PNG）讓讀者直觀看到異常趨勢；正常指標文字帶過即可，不需要附圖
- 敏感資訊（token、secret）已遮蔽

### 寫作風格

報告的目的是讓讀者快速吸收和行動。以下原則基於 NNG（Nielsen Norman Group）掃描閱讀研究、Cognitive Load Theory、Google Developer Documentation Style Guide，以及 Blameless Postmortem 文化共識。

**語氣定位——Knowledgeable Friend（Google Style Guide）**：像一個懂技術的同事在跟主管和團隊說明狀況。清楚、直接、容易吸收，但用語得體。

| 面向 | 做 | 不做 |
| --- | --- | --- |
| 語氣 | 專業白話（Professional Plain Language）：清楚直接，讀者不用想就能理解 | 書面腔（「使用者面向影響有限」）或輕挑口語（「塞爆了」「它幹了什麼」） |
| 表達形式 | 條列、表格為主，段落為輔——NNG 研究顯示 79% 讀者掃描而非逐字閱讀，結構化格式降低 extraneous cognitive load | 整段散文描述（wall of text）——迫使讀者花認知資源在解碼排版而非理解內容 |
| 精簡 | As concise as possible, but as wordy as necessary——用剛好夠的字讓人不用猜意思 | 砍到看不懂（過度精簡），或加字到囉嗦（冗餘） |
| 態度 | Blameless：焦點放在系統和流程，不放在個人。「How did the system allow this?」 | 批評個人或團隊，使用輕挑或嘲諷語氣 |
| 重複 | DRY（Don't Repeat Yourself）：同一個 fact 只出現在一個 section | 同一件事在多個 section 用不同措辭重述 |
| 未決策事項 | 只放「事實」和「已決定的事」。Action Items 是 AI 基於調查的初步建議（Proposed），明確標示需團隊討論確認 | 把建議寫成定案（如「P1 下週完成」），或替團隊做決策 |

## 事件報告模板

事件報告基於 **BLUF（Bottom Line Up Front）** 原則與 **Inverted Pyramid（倒金字塔）** 結構，採用 **3-30-300 Rule** 分層的 **Progressive Disclosure** 讓不同角色在各自的時間預算內找到需要的資訊。

| 層次 | 區塊 | 目標讀者 | 閱讀時間預算 |
| --- | --- | --- | --- |
| Header blockquote | 異常時段 + 影響 + 處置 | 所有人 | 3 秒 |
| 30 秒掌握全貌 | Executive Card（表格化事件名片） | 主管、TPM——讀到這裡即可做決策 | 30 秒 |
| 事件總覽 | 發生什麼事 + 時序 + 根因 + Action Items | Tech Lead + 牽涉到的團隊（前端/後端/SRE等）——了解來龍去脈和分工 | 5 分鐘（300 秒） |
| 跨團隊影響與流程檢討 | 各角色重點 + 為什麼沒有更早發現 | Tech Lead + 需要跨團隊協調的角色 | 延伸閱讀 |
| 技術調查細節 | 指標圖表 + 次要因素 + 排除假設 + 驗證 + 查詢來源 | 牽涉到的工程團隊 | 完整技術脈絡 |

每一層都是前一層的展開——「30 秒掌握全貌」自成完整結論（BLUF），不需要往下看也能做決策。

引導讀者的方式是 **Inverted Pyramid 排列 + Register Shift（語彙轉換）**，不是標注「某角色讀到這裡即可」：
- **BLUF**：Header blockquote（3 秒）+ Executive Card（30 秒）讓讀者快速掌握結論
- **Register Shift**：Executive Card 和事件總覽用業務語言（影響範圍、處置結果）；技術調查細節用技術語言（指標、query、code path）——語彙轉換本身就是隱形閘門，非技術讀者自然停止
- **Visual separator**：`---` 分隔線標記層次邊界

調查過程的逐行 code reference、查證段落、完整查詢指令不放在報告裡——那是調查 log，不是報告。報告末尾附「查詢來源」表讓需要的人自行追溯即可。

```markdown
# {日期} {事件名稱}

> **異常時段**：{起} ~ {迄} TWN
> **影響**：{一句話描述影響範圍}
> **處置**：{已完成的緊急處置}
>
> 「30 秒掌握全貌」可快速了解事件結論與後續安排；「事件總覽」涵蓋完整來龍去脈與行動項目；後續章節為延伸分析與技術調查細節。
```

| 面向 | 事件報告 | 定期掃描報告 |
