# 報告撰寫指引

報告目標讀者涵蓋前端、後端、Tech Lead、SRE、TPM、主管，乃至外部協作團隊，各方對系統背景的了解程度不一。報告的目的是讓多方**一次讀懂來龍去脈並知道下一步**，不是交代責任。因此：
- 技術細節（程式碼、查詢語法）可以簡單解釋，不用預設讀者一定懂
- 系統架構說明是幫讀者找出「這東西在哪」，不是在界定誰該負責
- 程式碼位置標籤不加「後端同仁參考」之類的觀眾限定語；任何需要了解的人都可以看

若專案有固定欄位、嚴重度定義、issue tracker 或 owner 標記方式，沿用實際慣例。

報告有兩種類型，依入口和情境選擇：
- **定期掃描報告**（入口 A）：週報 / 健檢，3-30-300 分層 + 收折式技術細節
- **事件報告**（入口 B / 特定問題調查）：四層 Progressive Disclosure（詳見事件報告專有設計）

---

## 共通原則

### 3-30-300 分層閱讀

兩種報告都遵循 **3-30-300 Rule**——投影在週會上，成員有主管、Tech Lead、前後端工程師，讓不同時間預算的讀者各取所需：

| 時間 | 讀者得到什麼 |
|------|------------|
| 3 秒 | 有幾件事、多嚴重 |
| 30 秒 | 每個問題怎麼回事、建議做什麼 |
| 300 秒 | 完整技術脈絡 |

具體的分層**機制**因報告類型而異（見各類型專有設計），但目標一致：不展開任何東西的讀者就能做決策。

### 數據與來源

- 每個數據點附查詢來源編號（`[Q1]`、`[ALB-Q1]` 等），讓讀者能自行驗證（詳見 `analysis-principles.md`「數據點附查詢來源」）
- 查詢來源編號只出現在技術細節區塊內（`<details>` 或底部技術章節）和證據/來源欄位中，敘事主文不放——會議投影時這些編號對多數讀者是雜訊
- 不同觀測層的數據標明來源：後端 application log ≠ CDN access log ≠ ALB access log，不混在同一行（見 `analysis-principles.md`「觀測層區分」）
- 語言精準：資料有混合結果時用限定語，不用絕對語句（見 `analysis-principles.md`「語言精準」）
- 敏感資訊（token、secret）已遮蔽

### 寫作風格

報告的目的是讓讀者快速吸收和行動。以下原則基於 NNG（Nielsen Norman Group）掃描閱讀研究、Cognitive Load Theory、Google Developer Documentation Style Guide，以及 Blameless Postmortem 文化共識。

**語氣定位——Knowledgeable Friend（Google Style Guide）**：像一個懂技術的同事在跟主管和團隊說明狀況。清楚、直接、容易吸收，但用語得體。

| 面向 | 做 | 不做 |
| --- | --- | --- |
| 語氣 | 專業白話（Professional Plain Language）：清楚直接，讀者不用想就能理解 | 書面腔（「使用者面向影響有限」）或輕挑口語（「塞爆了」「它幹了什麼」） |
| 表達形式 | 條列、表格為主，段落為輔——NNG 研究顯示 79% 讀者掃描而非逐字閱讀，結構化格式降低 extraneous cognitive load | 整段散文描述（wall of text）——迫使讀者花認知資源在解碼排版而非理解內容 |
| 精簡 | As concise as possible, but as wordy as necessary——用剛好夠的字讓人不用猜意思 | 砍到看不懂（過度精簡），或加字到囉嗦（冗餘） |
| 態度 | Blameless：焦點放在系統和流程，不放在個人。「How did the system allow this?」 | 批評個人或團隊，使用輕挑或嘲諷語氣 |
| 重複 | DRY（Don't Repeat Yourself）：同一個 fact 只出現在一個 section | 同一件事在多個 section 用不同措辭重述 |
| 未決策事項 | 只放「事實」和「已決定的事」。Action Items 是 AI 基於調查的初步建議（Proposed），明確標示需團隊討論確認 | 把建議寫成定案（如「高優先本週完成」），或替團隊做決策 |

**語氣光譜**（基於 Google / Microsoft Style Guide + Blameless Postmortem 文化）：

| 太正式 ❌ | 太口語 ❌ | 目標 ✅ |
| --- | --- | --- |
| 「使用者面向影響有限」 | 「平常使用無感」 | 「一般使用者不會感覺到異常」 |
| 「緊急處置手動清除所有 session 後」 | 「清掉所有 session」 | 「清除 Redis 後」 |
| 「流程面根因」 | 「為啥沒早點抓到」 | 「為什麼沒有更早發現」 |
| 「該因素之影響」 | 「它幹了什麼」 | 「影響」 |

**表達形式優先序**（基於 NNG 掃描閱讀研究 + Cognitive Load Theory）——結構化格式降低 extraneous cognitive load（讀者花在解碼排版的認知資源），讓讀者專注於理解內容本身：

1. **表格**——適合多屬性的結構化比較（根因分析、排除假設、Action Items、角色重點）
2. **條列（bullet points）**——適合事件描述、觀察列舉（發生什麼事）
3. **段落**——只用於需要上下文連貫的敘事（流程面根因等少數情境）

**精簡校準：**

- **Orwell's Third Rule**（「If it is possible to cut a word out, always cut it out」）：每句話都要有存在的理由
- **Einstein Principle**（「As simple as possible, but not simpler」→ 寫作版：As concise as possible, but as wordy as necessary）：如果多幾個字能避免讀者猜測，那幾個字不是贅字
- **DRY（Don't Repeat Yourself）**：同一個 fact 只出現在一個 section。事件時序裡寫過的事實，不在其他 section 重述

**模板彈性（Flexible Template）**——**「Only Include Relevant」**（Google SRE 精神）：模板是鷹架而非監獄。若某個 section（例如「各角色重點」或「排除的假設」）對這次事件不適用，請直接省略該區塊，**不要**填入「無」或湊字數。

### 標題與 Emoji 慣例

每個 issue 的標題用 **{主題emoji} + 一句白話摘要** 作為 h2。Emoji 代表問題的性質/主題，不代表嚴重度。嚴重度用分組標題或 metadata 行表達。選擇一眼能聯想到問題性質的 emoji。

### 技術細節隔離

兩種報告都將技術細節（code path、error flow、修改位置、查詢指令）與主要敘事分離，讓非技術讀者不需要穿越技術內容：
- **定期掃描**：各 issue 內用 `<details>` 收折——讀者按需展開特定問題的技術細節
- **事件報告**：底部獨立「技術調查細節」章節，用 Register Shift（語彙從業務語言轉為技術語言）作為隱形閘門

調查過程的逐行 code reference、查證段落不放在報告主文——那是調查 log，不是報告。

### 圖表

- 涉及基礎設施指標異常時，附 CloudWatch 圖表（PNG）讓讀者直觀看到趨勢
- 正常指標文字帶過即可，不需要附圖
- 描述放圖片下方 italic caption，不放 alt text（alt 渲染後不可見）
- 產圖方式見 `metrics-charts.md`

### 查詢來源與可重現性

兩種報告都附「查詢來源」參考表（編號 / 數據 / 工具 / 查詢範圍），讓每個數據點可追溯。完整 CLI 指令收折在 `<details>` 內供需要驗證的人重現。

### 行動清單

兩種報告共用相同欄位（排列順序見各自模板）：

| 欄位 | 說明 |
|------|------|
| 優先 | 🔴 高 / 🟡 中 / ⚪ 低 |
| 項目 | 建議動作 |
| 建議負責方 | 團隊/角色（非個人），無法判斷標 `❓` |
| 對應 issue | 指回報告內的 issue 段落標題（SSOT，技術細節由 issue 段落負責） |
| 完成標準 | 做到什麼算完成（有就填，無則留空） |
| 追蹤 | Jira 單號等（有就填，無則留空） |

報告產出後不預期有人回來更新內容。不確定的資訊用 `❓` 標記讓讀者一眼看出需要在會議上釐清。

### 語言

報告預設使用台灣正體中文（台灣軟體工程師慣用語，技術名詞保留原文）。使用者指定其他語言時從之。

## 定期掃描專有設計

### 讀者分層

| 時間 | 讀到哪裡 | 讀者 | 得到什麼 |
|------|---------|------|---------|
| 3 秒 | 「本次發現」severity-grouped summary | 主管 | 有幾件事、多嚴重 |
| 30 秒 | 各 issue 白話摘要 + 建議做法（不展開） | Tech Lead | 每個問題怎麼回事、該做什麼 |
| 300 秒 | 展開 `<details>` 技術細節 | 工程師 | 修復定位（code path、error flow、修改位置） |
| 按需 | 展開附錄「查詢指令」 | 需驗證的人 | 可重現所有數據 |

### Issue 展開面向

每個 🔴 高/🟡 中 問題展開以下六面向：

| 面向 | 目的 | 目標讀者 |
|------|------|---------|
| 情境 | 這個功能做什麼、為什麼存在 | 所有人——建立共同理解 |
| 錯誤流程 | error 從哪裡產生、怎麼傳播（ASCII flow 呈現跨系統路徑） | 前端/後端/外部團隊——找出「斷在哪一段」 |
| Root Cause | 程式碼位置和技術原因 | 負責修復的工程師 |
| 用戶影響 | 終端使用者看到什麼、功能是否受損 | Tech Lead / PM |
| 潛在議題 | 不修會怎樣、有什麼連鎖風險 | Tech Lead / PM |
| 建議 | 修法方向、方案比較、改動範圍 | 負責修復的工程師 |

⚪ 低 問題可精簡為表格呈現，不需要展開全部面向。

### 上次追蹤

偵測與時間範圍決定的流程在 SKILL.md 入口 A Step 0。此處僅定義輸出格式。

追蹤表每個項目標記狀態：
- ✅ **已改善**：error 消失或量體顯著下降（附本次數據佐證）
- 🔄 **仍存在**：error 仍在，量體無明顯變化
- ⚠️ **惡化**：量體上升
- ❓ **無法判斷**：本次掃描範圍未涵蓋、或需要人工確認

skill 只產出 data-based 的狀態，Jira 進度和實際處理狀態由團隊在週會上補充。

## 事件報告專有設計

事件報告基於 **BLUF（Bottom Line Up Front）** 原則與 **Inverted Pyramid（倒金字塔）** 結構，採用 **3-30-300 Rule** 分層的 **Progressive Disclosure** 讓不同角色在各自的時間預算內找到需要的資訊。每一層都是前一層的展開——「30 秒掌握全貌」自成完整結論，不需要往下看也能做決策。

### BLUF + Executive Card

Header blockquote + Executive Card 表格讓讀者快速掌握結論。

### Inverted Pyramid + Register Shift

引導讀者的方式是 **Inverted Pyramid 排列 + Register Shift（語彙轉換）**，不是標注「某角色讀到這裡即可」：
- Executive Card 和事件總覽用業務語言（影響範圍、處置結果）
- 技術調查細節用技術語言（指標、query、code path）——語彙轉換本身就是隱形閘門，非技術讀者自然停止
- `---` 分隔線標記層次邊界

| 層次 | 區塊 | 目標讀者 | 時間預算 |
| --- | --- | --- | --- |
| Header blockquote | 異常時段 + 影響 + 處置 | 所有人 | 3 秒 |
| 30 秒掌握全貌 | Executive Card（表格化事件名片） | 主管、TPM——讀到這裡即可做決策 | 30 秒 |
| 事件總覽 | 發生什麼事 + 時序 + 根因 + Action Items | Tech Lead + 牽涉到的團隊——了解來龍去脈和分工 | 5 分鐘（300 秒） |
| 跨團隊影響與流程檢討 | 各角色重點 + 為什麼沒有更早發現 | Tech Lead + 需要跨團隊協調的角色 | 延伸閱讀 |
| 技術調查細節 | 指標圖表 + 次要因素 + 排除假設 + 驗證 + 查詢來源 | 牽涉到的工程團隊 | 完整技術脈絡 |

### 事件時序

涵蓋完整生命週期：onset → peak → intervention（具體動作）→ recovery（指標回穩時間）。包含調查過程中的關鍵轉折：錯誤假設、排除方向、發現真因的時間點。

### 「發生什麼事」區塊

純文字 bullet points，不放圖表——保持讓非工程讀者快速掃描。圖表統一放「技術調查細節」。

### 「為什麼沒有更早發現」

引導思考：既有流程/監控哪裡有缺口？是否為跨產品共通風險？若有系統性根因（透過互動階段取得），用條列說明流程面原因。

## 結構差異速查

以下僅列出兩種報告的**專有結構元素**——共通元素（3-30-300、技術細節隔離、查詢來源+CLI、行動清單、圖表規則）見上方「共通原則」。

| 面向 | 事件報告專有 | 定期掃描專有 |
| --- | --- | --- |
| 敘事結構 | 單一事件時序敘事 | 多個獨立 issue 各自展開 |
| 速覽機制 | Executive Card（BLUF） | severity-grouped summary |
| 技術細節機制 | 底部獨立章節（Register Shift） | `<details>` 收折在各 issue 內 |
| 專有區塊 | 事件時序、跨團隊影響、排除假設、驗證方式、Changelog | 上次追蹤、error 每日趨勢、Log 雜訊調整建議、per-issue 建議做法表 |
| 篇幅 | ~120-170 行（含 Executive Card） | 依問題數量而定 |
